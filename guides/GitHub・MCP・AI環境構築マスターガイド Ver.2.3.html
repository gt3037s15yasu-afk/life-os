5. 再構築の完全手順

現在は再実行不要：すでにgithub: ✔ Connectedまで成功している。ここはPATの期限切れ・削除・Mac買替え・設定破損時の再現用。
0まず現状確認
cd ~/life-os
claude mcp list
✔ Connectedなら停止：再設定しない。そのまま「6. 接続・動作確認」へ進む。
1Fine-grained PATを作る
  1. GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens。
  2. Generate new tokenを押す。
  3. Token name：Claude Code MCP
  4. Expiration：90 days
  5. Repository access：Only select repositories → life-os
  6. Repository permissions：Contents＝Read and write
  7. Metadata＝Read-only（通常は自動）
  8. Generate tokenを押し、一度だけ表示されるPATをコピー。
絶対禁止：PATをChatGPT、Claude Codeの>、README、HTML、GitHub、スクリーンショットへ貼らない。
2Apple「パスワード」へ保存
  1. ⌘＋Space → 「パスワード」を開く。
  2. ＋で新規項目を作る。既存GitHubログインは編集しない。
  3. Webサイト：github.com
  4. ユーザ名：Claude Code MCP PAT
  5. パスワード欄：PATを貼付け。
  6. メモ：life-os限定／Contents R&W／期限
  7. 保存後、普通の文字をコピーし、クリップボード上のPATを上書き。
3古いgithub設定を削除

%が見える通常ターミナルで実行する。

cd ~/life-os
claude mcp remove github

No github MCP server is currently configuredなら、すでに削除済み。次へ進んでよい。

4PATを一時変数へ非表示入力
read -s "GITHUB_PAT?PATを貼り付けてEnter（非表示）: "; echo

Apple「パスワード」からPATをコピーし、この入力待ち画面で貼り付けてReturn。文字も●も表示されないのが正常。

[[ -n "$GITHUB_PAT" ]] && echo PAT_OK || echo PAT_MISSING

PAT_OKなら成功。PAT_MISSINGなら、再度コピーしてこの手順だけやり直す。

5Claude CodeへGitHub MCPを登録

今回、Claude Code v2.1.216で実際に成功した形式：

claude mcp add-json github '{"type":"http","url":"https://api.githubcopilot.com/mcp/","headers":{"Authorization":"Bearer '"$GITHUB_PAT"'"}}'

登録後、シェル上の一時変数を消し、接続状態を確認する。

unset GITHUB_PAT
claude mcp list
成功表示：github: https://api.githubcopilot.com/mcp/ (HTTP) - ✔ Connected
重要な補足：非表示入力はターミナル画面や履歴への露出を減らす方法。PATを含むAuthorizationヘッダーはClaude Codeのローカル設定に保存されるため、Macのログイン・ディスク・バックアップも保護する。設定ファイルをGitHubへCommitしない。

8. セキュリティとAI開発の運用規律

秘密情報の必須ルール

  • Fine-grained PATと最小権限を使う
  • 対象Repositoryをlife-osだけに限定する
  • 有効期限と失効手順を持つ
  • 秘密はKeychain・環境変数・Secret Storeへ保存する
  • 会社用と個人用Repositoryを分離する
  • 漏えい疑いは確認より先に失効する

絶対にしない

  • PAT・API Keyを会話へ貼らない
  • README・HTML・コードへ直書きしない
  • スクリーンショットへ映さない
  • mainへ無確認で直接変更しない
  • 削除・外部送信・Mergeを無条件自動化しない
  • 未検証のHookを信頼して実行しない

きれいなコーディングをAIの型にする

Single Responsibility1ファイル・1関数・1ツールの責務を小さく保つ。
Readable Naming人が読んで目的が分かる名前とフォルダ構造にする。
Small Diff1タスク1Branch。関係ない変更を混ぜない。
Test & Lint変更後に自動検証し、結果をPRへ残す。
Secrets Outside Code認証情報を成果物と履歴から分離する。
Human Approval破壊的・高コスト・外部影響のある操作はYasuが承認する。
Security → Cloudの順序：セキュリティは最後に足す機能ではなく、今から全段階へ埋め込む。Cloud化は、Secrets・権限・ログ・Approval・Rollback・会社／個人分離を確認した後にだけ進める。

10. 重要概念の役割分担

似た言葉を同じものとして扱わないことが、後で複雑化しない最大のポイント。

Project関連Chat・Source・Local folderをまとめる「仕事場」。Agentそのものではない。
Tool一つの明確な処理を行う最小部品。入力・出力・権限・副作用を定義する。
Workflow / Flow複数Toolを決められた順序、条件分岐、承認、Retryでつなぐ手順。
Skill繰り返し使う仕事のInstructions、References、Scriptsをまとめた再利用可能な能力。
MCPGitHub、Calendar、Drive等の外部SystemやToolへAgentを接続する共通規格。
HookSession開始、Tool使用前後、Stop等のLife Cycleで決定論的Scriptを動かす仕組み。
Agent目的とContextを受け、判断し、Tool／Workflowを選び、結果を完成させる実行主体。
Sub-agent調査、実装、Test、Security等の狭い役割へ分けた専門Agent。
Orchestrator大きな目的を分解し、Agent・Workflow・Toolを選び、進捗・競合・結果を統合する管理層。
AGENTS.mdCodexがRepository内で毎回守るBuild、Test、Review、命名、承認等の永続ルール。
概念一言で言うとLife-OSでの位置づけ
ToolできることHTML Dashboard、Calculator、Checker、Connector
Skillうまく使う方法標準手順・品質基準・再利用Script
Workflow実行順序Toolの連鎖、条件分岐、Approval、Retry
Hook決まった時点の自動処理Secret Scan、Lint、Log、Stop時検証
Agent状況判断する担当者目的に合わせてWorkflowを選択・管理
Sub-agent専門担当Security、Research、Implementation、Test
Orchestrator全体管理者Goal分解、配車、状態管理、統合、承認要求

13. AgentからOrchestratorへ：Life-OSの最終構成

Layer担当主な責任
Human GovernanceYasuGoal、Priority、価値判断、最終承認、停止判断
OrchestratorAI ManagerGoal分解、Agent選択、順序、状態、Conflict、結果統合
Agents専門担当仕事・資産・健康・学習・開発等のDomain判断
Sub-agents作業担当Research、Implementation、Review、Test、Security
Workflows / Skills標準作業再現可能な手順、Approval、Retry、品質基準
Tools / MCP実行部品Calendar、Mail、Drive、GitHub、HTML、Calculator、API
Data / HistoryGitHub・Drive等正本、Context、Version、Trace、証拠

Orchestratorの標準Loop

  1. YasuのGoalと制約を受け取る。
  2. Tool Registry、Workflow、Skill、Agent一覧から使える能力を確認する。
  3. Goalを独立したWorkstreamへ分解する。
  4. 必要なAgent／Sub-agentへScope、Input、終了条件、権限を付けて割り当てる。
  5. 結果、Error、Trace、費用、Conflictを集約する。
  6. 高Risk操作は停止し、Yasuへ具体的なApprovalを求める。
  7. 承認後に反映し、GitHubへ履歴・学び・次の改善を残す。
Projectとの違い：Projectは仕事場。Agentはその仕事場で判断する担当者。Orchestratorは複数の仕事場・Agent・Workflowを横断して配車する管理者。
最終像：「あれとこれを組み合わせたら何ができるか」をOrchestratorがTool RegistryとContextから判断し、複数Agentへ仕事を割り振る。ただしYasuがHuman Orchestrator／CEOとして目的と最終承認を保持する。
